# Q4: Registration-day connection leak

## (a) Output of the original code
See [`q4_connections/leaky.py`](../q4_connections/leaky.py) and [`outputs/q4_leaky.txt`](../outputs/q4_leaky.txt).
```
connection opened, open = 1
found student 1
connection closed, open = 0
connection opened, open = 1
error: bad id
connection opened, open = 2
found student 2
connection closed, open = 1
open connections now: 1
```
When `lookup(-1)` raises, the exception leaves the function before `conn.close()` runs, so that connection is never closed (leaked). Every wrong ID leaks one more. After MAXCONN wrong IDs all connections are in use, so nobody else can log in and registration stops.

## (b) Fix with `with`
See [`q4_connections/fixed.py`](../q4_connections/fixed.py) and [`outputs/q4_fixed.txt`](../outputs/q4_fixed.txt). `__exit__` always runs, whether the block ends normally or with an exception. Final line: `open connections now: 0`.

## (c) Person, Student, GradStudent
See [`q4_connections/people.py`](../q4_connections/people.py) and [`outputs/q4_people.txt`](../outputs/q4_people.txt).

- **Construction order:** Person -> Student -> GradStudent.
- **Cleanup order:** GradStudent -> Student -> Person (the reverse).

Why: a child is built on top of its parent's parts, so the parent must exist first. During cleanup the child may still use its parent's parts, so the child is cleaned first and the parent last (like unstacking building blocks from the top).

## (d) Why not `finalize()` / `__del__`?
These run only when the garbage collector decides to collect the object. That may be much later, or never (for example at program exit), so the connection stays held and the pool can still fill up. Also: exceptions inside them are ignored, reference cycles can delay them, and Java's `finalize()` is deprecated for removal.

C++ destructors are **deterministic**: they run exactly when the object leaves scope, even while an exception is unwinding the stack. This pattern is called **RAII** (Resource Acquisition Is Initialization).
