# Q5: The diamond problem

## (a) Diagram and problems
```
            Person
           /      \
      Student    Staff
           \      /
       TeachingAssistant
```
1. **Duplicate data:** the TA inherits `Person` along two paths, so it can end up with two copies of `name`, and it is unclear which is the real one.
2. **Method clash:** `Student` and `Staff` both define `role()`, so it is ambiguous which one the TA gets. The old system picked one and lost the other.

## (b) Code
[`q5_diamond/diamond.py`](../q5_diamond/diamond.py). Output: [`outputs/q5_diamond.txt`](../outputs/q5_diamond.txt).
Python's method resolution order (TA -> Student -> Staff -> Person) makes `super()` reach `Person` once, so there is a single `name`.

## (c) Table
| | C++ | Python | Java |
|---|---|---|---|
| Can a class have several class parents? | Yes | Yes | No (one class parent; many interfaces) |
| How is the duplicate-Person problem solved? | `virtual` inheritance (`: virtual public Person`) | Automatically by the MRO (C3 linearisation) and `super()` | Does not arise: interfaces hold no instance data |
| How is the `role()` clash solved? | Override in TA, or qualify `Student::role()`; otherwise ambiguous (compile error) | Override in TA and call `Student.role(self)`; otherwise first in MRO wins | TA must override default methods and may call `Student.super.role()` |

## (d) Avoiding multiple inheritance
1. **Complexity and ambiguity:** diamonds, MRO and virtual inheritance are easy to get wrong and hard to debug.
2. **Roles change over time:** a TA is not a new kind of person; it is a person who currently holds two roles. Inheritance is fixed when the object is created, so a role cannot be added or dropped at run time, and every role combination would need its own class.
